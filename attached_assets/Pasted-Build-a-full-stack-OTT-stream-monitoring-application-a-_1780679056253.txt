Build a full-stack OTT stream monitoring application (a broadcast NOC tool) that replaces an existing WordPress monitoring wall. It monitors two independent layers: (1) the live HDMI outputs of physical OTT devices (Roku, Fire TV, Chromecast, Apple TV) captured and served as WebRTC streams by an SRS media server, and (2) the source HLS (.m3u8) streams distributed to all OTT platforms. It includes automated failure detection, incident tracking, and alerting.
Context / Existing Infrastructure

SRS server (WebRTC, WHEP): WebRTC playback uses SRS WHEP endpoints in this exact form: http://cdn1.obedtv.live:2023/rtc/v1/whep/?app=live&stream={streamkey}. Example for Roku: http://cdn1.obedtv.live:2023/rtc/v1/whep/?app=live&stream=vodroku.
Current device streams (one per physical device's HDMI capture): vodroku (Roku), vodfire (Firestick), vodchrome (Chromecast), vodapple (Apple TV).
SRS HTTP API for stream state (active publishers, clients, bitrate). Assume base http://cdn1.obedtv.live:1985/api/v1/ but make it fully configurable in settings — confirm/override at runtime.
RTMP ingest for the ffmpeg detection worker. Assume rtmp://cdn1.obedtv.live:1935/live/{streamkey} but make it configurable in settings.
Guacamole remote-control session embedded via iframe for device control. URL is configurable; seed with http://cdn3.obedtv.live:8088/guacamole/#/client/MQBjAG15c3Fs.

CRITICAL: Mixed-content / HTTPS proxy requirement
The app will be served over HTTPS (in a container behind TLS), but the SRS WHEP endpoint, SRS HTTP API, and Guacamole are plain HTTP. Browsers block mixed content, so the frontend must NOT call these HTTP endpoints directly. Instead:

The FastAPI backend must expose a reverse-proxy passthrough for all HTTP upstreams (SRS WHEP, SRS API, and the Guacamole iframe), so the browser only ever talks HTTPS to our own origin and the backend relays to the HTTP upstreams internally.
Implement a WHEP proxy route, e.g. POST /api/proxy/whep?stream={streamkey} that forwards the browser's SDP offer to the real SRS WHEP HTTP endpoint and returns the SDP answer. The frontend SRS SDK must point at this HTTPS proxy route, never at http://cdn1.obedtv.live:2023 directly.
Implement an SRS API proxy route, e.g. GET /api/proxy/srs/streams, that the backend uses/serves over HTTPS.
For Guacamole, proxy or embed it through an HTTPS-safe path so the iframe doesn't trip mixed-content blocking (reverse-proxy the Guacamole HTTP origin through the backend).
All upstream HTTP base URLs are stored in DB settings; the proxy reads them from there. Never hardcode upstream endpoints in frontend source.

Tech Stack (use exactly this)

Frontend: React + Vite, TypeScript, Tailwind CSS.
Backend: Python FastAPI (SQLAlchemy ORM + Alembic migrations).
Database: PostgreSQL.
WebRTC playback: SRS official WebRTC SDK (srs.sdk.js / SrsRtcWhipWhepAsync, WHEP). Browser playback goes through the backend WHEP proxy described above. Do NOT use the WordPress SRS plugin and do NOT use HLS for the device tiles (keep WebRTC low-latency).
HLS playback (optional operator eyeball view): hls.js.
Real-time updates: Server-Sent Events (SSE) from FastAPI to push status changes live to the dashboard.

Data Model (PostgreSQL)

devices: id, name, platform, srs_stream_key, srs_app (default "live"), enabled (bool), guacamole_url (nullable), notes.
hls_streams: id, name, master_url, enabled (bool), expected_renditions (int, nullable), is_encrypted (bool), notes.
check_results: id, device_id (nullable), hls_stream_id (nullable), timestamp, status, detail (JSON), frame_thumbnail_path (nullable). Each row belongs to either a device or an HLS stream.
incidents: id, device_id (nullable), hls_stream_id (nullable), started_at, resolved_at (nullable), status, reason, acknowledged_by (nullable).
settings: key/value config store (all endpoints, intervals, thresholds, webhooks).

Core Features
1. Monitoring Wall (main view)

Responsive, dense grid of device tiles, broadcast-NOC dark theme. Each tile:

Device name/label + platform.
Live WebRTC video player (SRS WHEP via the HTTPS proxy; autoplay, muted by default, unmute toggle).
Status badge: HEALTHY (green), WARNING (amber), DOWN (red), UNKNOWN (gray).
Last-checked timestamp and current failure reason (e.g. "Black frame 12s", "No publisher", "Audio silent").
Bitrate/publisher indicator from the SRS API (via proxy).
Auto-reconnect the WebRTC player if the stream drops.


A second section/tab "Source Streams" for HLS health cards (see below).
A collapsible side panel embedding the Guacamole iframe (through the HTTPS-safe proxy path) for remote device control. URL configurable in settings.

2. Device Registry (data-driven)

CRUD admin UI for devices. Adding/editing a device is a form, never a code change. The wall renders from this table. Seed with the four existing devices.

3. HLS Stream Registry (data-driven)

CRUD admin UI for hls_streams. Adding a stream is a form, never a code change. Seed empty (operator adds master URLs after build) unless URLs are provided.

4. Device Health Detection (background worker)
For each enabled device, every 15s (configurable):

SRS API check: poll the SRS streams API (via internal proxy) and confirm the device's stream has an active publisher. No publisher → DOWN ("No publisher").
Frame analysis check: run ffmpeg against the RTMP ingest URL with these filters: blackdetect=d=2:pix_th=0.10, freezedetect=n=0.003:d=2, silencedetect=n=-50dB:d=3. Parse ffmpeg stderr for detections.
Status mapping: black OR frozen OR no-publisher → DOWN; audio-silent-only → WARNING; all clear → HEALTHY.
Capture a JPEG frame grab on each DOWN/WARNING transition and store its path for the alert.

5. HLS Health Detection (separate background worker)
For each enabled HLS stream, every 30s (configurable):

Master manifest fetch — GET the master .m3u8: check HTTP 200, latency (ms), valid #EXTM3U. Fail → DOWN ("Manifest unreachable"/"Invalid manifest").
Rendition audit — parse master, confirm every #EXT-X-STREAM-INF variant URL is reachable; compare count to expected_renditions if set. Missing variant → WARNING.
Segment liveness — read #EXT-X-MEDIA-SEQUENCE/newest segment from each variant playlist; on the next poll confirm it advanced. Not advancing over 2 polls → DOWN ("Stream stalled"). This is the critical live-freeze check.
Segment fetch — download the newest 1–2 segments from the top rendition: HTTP 200, non-zero size, throughput. 404/stale → DOWN ("Segment fetch failed").
Decode validation (deep, toggleable) — ffprobe a fresh segment: confirm video + audio streams, valid codec, plausible duration. Corrupt → DOWN ("Segment decode failed").
DRM/key check — if is_encrypted, confirm the #EXT-X-KEY URI resolves (HTTP 200). Unreachable → DOWN ("Key server unreachable").

Use httpx (async) for all HTTP/manifest/segment work, the m3u8 PyPI library to parse playlists, and ffprobe as an async subprocess with a timeout. Store per-check metrics in detail JSON (manifest latency, throughput, media-sequence, rendition count, segment duration) for graphs.
6. Shared detection logic

Both workers run as independent async background tasks sharing one DB, settings, debounce logic, incident model, SSE feed, and alerting pipeline. Factor incident/alert handling into a shared service both workers call — do not duplicate it.
Debounce: a monitored item's official status only changes after 2 consecutive checks agree (kills flapping/false positives).
ffmpeg/ffprobe must run as async subprocesses with timeouts, never blocking the event loop. Limit concurrent ffmpeg/ffprobe processes (configurable, default 4).

7. Incidents & History

An incident opens on a healthy→bad transition and closes on recovery. Shared across devices and HLS streams.
Per-item incident timeline + a global incident feed. Show uptime % and MTTR per item over selectable windows (24h, 7d, 30d). Ability to acknowledge an active incident.

8. Alerting

On a new debounced incident, send a webhook alert. Support Slack/Discord incoming webhook and generic webhook. Payload includes item name, type (device vs source stream), reason, timestamp, failing rendition (HLS) if applicable, and the captured frame thumbnail (devices). Send auto-resolve ("recovered") notifications too.
Alerting config (webhook URLs, enable/disable per channel, alert-on-DOWN vs also-WARNING) stored in settings and editable in the UI.

9. Settings (all in DB, no hardcoded endpoints)

SRS WHEP base URL, SRS HTTP API base URL, RTMP ingest base URL, default Guacamole URL, device check interval, HLS check interval, debounce count, ffmpeg thresholds, segment-stall threshold, ffprobe enable/disable toggle, max concurrent ffmpeg/ffprobe, alert webhooks. Provide a .env.example with fallbacks.

Architecture Requirements

Clean split: /backend (FastAPI app, models, workers, proxy routes, shared incident/alert service, routers) and /frontend (React/Vite).
FastAPI REST API + one SSE endpoint (/api/stream/status) that pushes status changes so badges update without polling.
All browser→upstream HTTP traffic goes through backend HTTPS proxy routes (WHEP, SRS API, Guacamole) to avoid mixed-content blocking.
Everything data-driven: operators add devices/streams, change endpoints, and set webhooks via UI — never by editing code.
Build for scale: grid, workers, and schema must handle 4 items today and 40+ later without rework.

Important Constraints

Do NOT use WordPress or any WP plugin.
Use the SRS official WHEP SDK for device playback (low-latency WebRTC), routed through the HTTPS proxy. Use hls.js only for the optional HLS eyeball view.
The HTTPS-over-HTTP mixed-content proxy is mandatory — the app is served via HTTPS and all SRS/Guacamole upstreams are HTTP.
Make everything configurable and data-driven; the operator should never edit source to add an item, change an endpoint, or update a webhook.
